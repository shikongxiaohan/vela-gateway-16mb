# 表盘 / 快应用安装

资源页提供自定义表盘与快应用的安装功能。实现方式与现有第三方工具（AstroBox / minstall）一致：文件先传输至网关并存储于 Flash，再由网关通过蓝牙 SPP，经小米穿戴 Mass 通道分片推送至手表。

网关仅负责数据传输，不对文件解包，也不校验表盘结构。安装异常时可在手表端删除后重新安装。

## 前置条件

- 手表与网关已完成连接，首页显示「连接正常」
- 手表剩余空间不小于文件体积。空间不足时将在最后一步返回失败
- 表盘格式为 `.bin` 或 `.face`，快应用格式为 `.rpk`
- 安装过程中应保持供电与链路稳定，连接中断需重新执行

## 操作步骤

1. 移动设备访问管理台，进入「资源」页
2. 「表盘文件」选择 `.bin` / `.face`，「快应用包」选择 `.rpk`，选择后自动上传
3. 上传完成后列表新增一行，点击「安装」
4. 进度条完成且状态变为 `done` 表示安装成功

无需保留的文件可点击「删除」释放空间。SPIFFS 总容量 3.8 MB，两类文件共用，扣除为日志与录音预留的 96 KB 后，可用空间约 3.7 MB。

## 安装期间的网络行为

Mass 通道独占蓝牙链路，因此安装期间网关直接丢弃回程网络数据包。该路径不提供排队缓冲，排队将导致 RAM 耗尽。手表侧 TCP 连接将自行重传，安装完成后恢复正常，表现为数秒内网络无响应。

3 MB 表盘在典型链路质量下需数分钟完成。安装期间建议避免在手表端执行高带宽操作，以免延长传输时间。

## 失败原因

管理台显示简要原因，串口日志提供详细信息。

| 提示 | 含义 | 处理方式 |
|---|---|---|
| `wf_prepare_timeout` | 未收到表盘握手响应 | 确认手表处于解锁状态且蓝牙连接正常，重新尝试 |
| `mass_prepare_timeout` | 未收到 Mass 握手响应 | 同上。也可能为手表忙碌，稍后重试 |
| `prepare_rejected status=N` | 手表拒绝了请求 | N 为设备返回的原因码，通常为空间不足或版本不兼容 |
| `mass_prepare_failed status=N` | Mass 通道拒绝接收 | 空间不足或数据校验未通过 |
| `part_ack_timeout 12/340` | 第 12 片发出后 4 秒内未收到回执 | 缩短设备间距离后重试，链路质量较差时常见 |
| `install_failed status=N` | 文件传输完成但安装失败 | 检查手表端是否已存在新表盘 |
| `timeout` | 整体超时，默认 10 分钟 | 文件过大或链路质量不足，重新尝试 |
| `out_of_memory` / `no_scratch` | 网关内存不足 | 重启网关，关闭手表端占用网络的应用 |
| `file_open_failed` / `file_read_failed` | Flash 文件无法打开或读取不完整 | 删除后重新上传，通常由上传过程中断引起 |
| `cancelled` | 用户取消 | |

## 文件存储

SPIFFS 中文件名为固定格式：

| 文件名 | 含义 |
|---|---|
| `W0.bin` ~ `W5.bin` | 表盘，最多 6 个 |
| `A0.rpk` ~ `A3.rpk` | 快应用，最多 4 个 |

表盘 ID 位于文件偏移 `0x28`，格式为十进制 ASCII；表盘名称位于 `0x68`。快应用的包名与版本号从 `.rpk` 内的 `manifest.json` 读取，`.rpk` 文件本身为 zip 格式。网关仅解压该条目，使用 ESP32 ROM 内置 inflate 实现，不产生额外内存开销。

## 协议细节

以下内容供自行实现时参考。

外层为 WearPacket：

```
A5A5 | type(1) | seq(1) | len(2 LE) | crc16(2 LE) | payload
```

安装流程分四步：

1. WatchFace/prepare（type=4, id=4），携带表盘 ID、长度与 `version=65536`，等待设备返回 READY
2. Mass/prepare（type=22, id=0），携带 `data_type`、md5 与长度，设备返回 `expected_slice_length`
3. 通过 Mass 通道逐片发送，每片等待 ACK，`fragment_max = expected_slice_length - 6`
4. 等待 WatchFace/report_install_result（type=4, id=5）

`data_type` 取值：表盘为 16，快应用为 64。

数据块格式：`comp(1)=0 | data_type(1) | md5(16) | length(4 LE) | 文件字节 | crc32(4 LE)`，其中 crc32 覆盖前五个字段。

分片格式：`channel(1)=2 | op(1)=1 | total(2 LE) | cur(2 LE, 从 1 开始) | fragment`。

快应用 prepare 的字段号尚未在真机上验证。当前实现采用 `ThirdpartyApp{field22 → {1:package, 2:versionCode, 3:size}}`，命令 id=1。首次测试建议以表盘为对象。

字段号错误不会产生报错，表现为设备静默无响应，因此 `tools/test_watchface_install.py` 对这些数值做了固定校验。修改协议实现前应先执行该测试。

## mass_prepare 诊断

该步骤的响应字段号尚未完全确定，因此未获取到合法状态时，固件会输出原始响应包，无需修改代码或开启开关：

```
WF_INSTALL_PREPARE_RAW mass len=14 08161000C2010A...
WF_INSTALL_PREPARE_SUB field=24 len=8 10 00 12 02 ...
WF_INSTALL_CAND sub=24 off=2=18
WF_INSTALL_CAND sub=24 off=5=2
```

`_RAW` 为解密后的完整 protobuf。`_SUB` 为外层 oneof（field 6 / 22 / 24）各自的子字节串。`_CAND` 按位置无关的方式列出各候选字节的十进制值，不依赖 `Mass{2}/PrepareResponse` 这一层包装，即使包装层判断错误也能定位到 `0` 与 `expected_slice_length`。

结合上述三组输出可确定字段号错误的层级。
