# 表盘 / 快应用安装

「资源」页可以让手表装自定义表盘和快应用。做法跟米坛社区那套工具（AstroBox / minstall）一样：文件先传到网关存进 Flash，再由网关通过蓝牙 SPP 走小米穿戴的 Mass 通道分片推给手表。

网关只管搬，不解包，也不检查表盘结构对不对。装坏了在手表上删掉重装就行。

## 用之前

- 手表已经跟网关联上，首页显示「连接正常」
- 手表剩余空间够放这个文件。手表满了会在最后一步报失败
- 表盘是 `.bin` 或 `.face`，快应用是 `.rpk`
- 装的过程中别拔电，也别走远，断链了得重来

## 操作

1. 手机打开管理台，点「资源」
2. 「表盘文件」选 `.bin` / `.face`，「快应用包」选 `.rpk`，选完就自动上传
3. 上传完列表里多一行，点「安装」
4. 进度条走完、状态变成 done，就是装上了

不用了点「删除」腾空间。SPIFFS 一共 3.8 MB，两类文件共用，扣掉留给日志和录音的 96 KB，实际能放 3.7 MB 左右。

## 装的时候网会断一下

Mass 通道要独占蓝牙，所以安装期间网关会把回程的网络包直接丢掉。这里不能排队，一排就把 RAM 吃光了。手表上的 TCP 会自己重传，装完就恢复，表现就是这几秒网卡住了。

一个 3 MB 的表盘要几分钟，看链路质量。装的时候别在手表上刷视频，越刷越慢。

## 失败原因

管理台会显示一句原因，串口日志里有更详细的。

| 提示 | 意思 | 怎么办 |
|---|---|---|
| `wf_prepare_timeout` | 手表没回表盘握手包 | 确认手表解着锁、蓝牙连着，重试一次 |
| `mass_prepare_timeout` | 手表没回 Mass 握手包 | 同上。也可能是手表正忙，等一下再试 |
| `prepare_rejected status=N` | 手表明确拒绝了 | N 是设备给的原因码，多半是空间不够或者版本不适配 |
| `mass_prepare_failed status=N` | Mass 通道不肯收 | 空间不够，或者数据校验不过 |
| `part_ack_timeout 12/340` | 第 12 片推过去 4 秒没回执 | 走近点再试。链路差的时候常见 |
| `install_failed status=N` | 文件发完了，手表说装失败 | 看看手表上是不是已经有新表盘了 |
| `timeout` | 整体超时，默认 10 分钟 | 表盘太大或者链路太差，重试 |
| `out_of_memory` / `no_scratch` | 网关内存被挤爆 | 重启网关，关掉手表上占网的应用 |
| `file_open_failed` / `file_read_failed` | Flash 里的文件打不开或者读不全 | 删掉重新上传，多半是上传时断过 |
| `cancelled` | 自己点了取消 | |

## 文件怎么存的

SPIFFS 里的文件名是固定的：

| 文件名 | 含义 |
|---|---|
| `W0.bin` ~ `W5.bin` | 表盘，最多 6 个 |
| `A0.rpk` ~ `A3.rpk` | 快应用，最多 4 个 |

表盘 id 在文件偏移 `0x28`，是十进制 ASCII；表盘名在 `0x68`。快应用的包名和版本号从 `.rpk` 里的 `manifest.json` 读，`.rpk` 本身是个 zip。网关只解这一个条目，用 ESP32 ROM 里的 inflate，不额外占内存。

## 协议细节

自己实现的话看这节。

外层是 WearPacket：

```
A5A5 | type(1) | seq(1) | len(2 LE) | crc16(2 LE) | payload
```

安装分四步：

1. WatchFace/prepare（type=4, id=4），带表盘 id、长度、`version=65536`，等设备回 READY
2. Mass/prepare（type=22, id=0），带 `data_type`、md5、长度，设备回 `expected_slice_length`
3. 走 mass 通道逐片发，每片等 ACK，`fragment_max = expected_slice_length - 6`
4. 等 WatchFace/report_install_result（type=4, id=5）

`data_type` 表盘是 16，快应用是 64。

数据块：`comp(1)=0 | data_type(1) | md5(16) | length(4 LE) | 文件字节 | crc32(4 LE)`，crc32 覆盖前五段。

分片：`channel(1)=2 | op(1)=1 | total(2 LE) | cur(2 LE, 从 1 开始) | fragment`。

快应用 prepare 的字段号还没在真机上验证过。当前用的是 `ThirdpartyApp{field22 → {1:package, 2:versionCode, 3:size}}`，命令 id=1。第一次测建议先拿表盘练手。

字段号写错不会报错，只会让手表静默不理你，所以 `tools/test_watchface_install.py` 把这些数字钉住了。改协议之前先跑一遍。

## 卡在 mass_prepare 看串口

这一步的应答字段号最没把握，所以只要没拿到合法状态，固件就会把原始回包打出来，不用改代码也不用开开关：

```
WF_INSTALL_PREPARE_RAW mass len=14 08161000C2010A...
WF_INSTALL_PREPARE_SUB field=24 len=8 10 00 12 02 ...
WF_INSTALL_CAND sub=24 off=2=18
WF_INSTALL_CAND sub=24 off=5=2
```

`_RAW` 是解密后的完整 protobuf。`_SUB` 是外层 oneof（field 6 / 22 / 24）各自的子字节串。`_CAND` 把每个候选字节的十进制值都列了一遍，跟位置无关，故意不依赖 `Mass{2}/PrepareResponse` 这层包装，包装层猜错也能找到 0 和 `expected_slice_length`。

把这几个都拿出来，就能定位是哪一层字段号不对。
