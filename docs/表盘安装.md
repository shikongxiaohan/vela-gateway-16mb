# 表盘 / 快应用安装

管理台「资源」标签可以把自定义表盘和快应用装到手表上。原理和米坛社区那套自定义表盘工具（AstroBox / minstall）一样：把文件先传到网关的 Flash 里，再由网关通过蓝牙 SPP 走小米穿戴的 **Mass 数据通道**分片推给手表。

网关只当搬运工 —— 不解包、不校验表盘结构以外的任何东西，装坏了在手表上删掉重装即可。

---

## 用之前

- 手表要先跟网关联上（管理台首页「连接正常」）
- 手表剩余空间够放这个表盘/应用（手表侧满了会在最后一步报失败）
- 表盘文件是 `.bin` 或 `.face`，快应用是 `.rpk`
- 别在装的时候拔电或走远 —— 装到一半断链要重来

## 操作

1. 手机浏览器打开管理台，点「资源」
2. 「表盘文件」选 `.bin` / `.face`，「快应用包」选 `.rpk`，选完自动上传
3. 上传完列表里会出现一行，点「安装」
4. 进度条走完、状态变成 **done** 就是装好了

不用的时候点列表里的「删除」腾空间。设备上 3.8 MB 全给这两类文件用，留了 96 KB 给日志/录音，所以实际上限约 3.7 MB。

## 装的时候网会断一下

安装期间 Mass 通道独占蓝牙，网关会把回程的网络包**直接丢弃**（不排队，排队会吃光 RAM）。手表上的 TCP 有重传，装完自动恢复，表现就是这几秒网卡住了 —— 正常的。

一个 3 MB 的表盘大约几分钟，取决于链路质量。装的时候别在手表上刷视频，越刷越慢。

## 失败了怎么看

管理台会显示失败原因，串口日志里有更详细的一行：

| 提示 | 意思 | 怎么办 |
|---|---|---|
| `wf_prepare_timeout` | 手表没回表盘握手包 | 确认手表解着锁、蓝牙连着；重试一次 |
| `mass_prepare_timeout` | 手表没回 Mass 握手包 | 同上；设备可能正忙，等一下再试 |
| `prepare_rejected status=N` | 手表明确拒绝了 | `N` 是设备给的原因码；多半是空间不够或版本不适配 |
| `mass_prepare_failed status=N` | Mass 通道拒绝接收 | 空间不够 / 数据校验不过 |
| `part_ack_timeout 12/340` | 第 12 片推过去 4 秒没回执 | 走近点再试；链路差时常见 |
| `install_failed status=N` | 文件发完了，手表说装失败 | 看手表上是否已经出现新表盘 |
| `timeout` | 整体超时（10 分钟） | 表盘太大或链路太差，重试 |
| `out_of_memory` / `no_scratch` | 网关内存被挤爆 | 重启网关，关掉手表上占网的应用 |
| `file_open_failed` / `file_read_failed` | Flash 里的文件打不开或读不全 | 删掉重新上传（多半是上传时断过） |
| `cancelled` | 自己点了取消 | — |

串口里会打原始回包十六进制（`WF_INSTALL_PREPARE_RAW`），协议对不上时拿它比对。

## 文件是怎么存的

网关的 SPIFFS 里，槽位命名固定：

| 文件名 | 含义 |
|---|---|
| `W0.bin` ~ `W5.bin` | 表盘，最多 6 个 |
| `A0.rpk` ~ `A3.rpk` | 快应用，最多 4 个 |

表盘 id 在文件偏移 `0x28`（十进制 ASCII），表盘名在 `0x68`；快应用的包名和版本号从 `.rpk`（就是个 zip）里的 `manifest.json` 读。网关只解这一个文件，用 ESP32 ROM 里的 inflate，不占额外内存。

## 协议细节（要自己实现的话看这里）

外层是 WearPacket：`A5A5 | type(1) | seq(1) | len(2 LE) | crc16(2 LE) | payload`。

安装走四步：

1. **WatchFace/prepare**（type=4, id=4）带表盘 id、长度、`version=65536` → 等设备回 READY
2. **Mass/prepare**（type=22, id=0）带 `data_type`、md5、长度 → 设备回 `expected_slice_length`
3. `<mass>` 通道逐片发，每片等 ACK，`fragment_max = expected_slice_length - 6`
4. 等 **WatchFace/report_install_result**（type=4, id=5）

`data_type`：表盘 `16`，快应用 `64`。

数据块：`comp(1)=0 | data_type(1) | md5(16) | length(4 LE) | 文件字节 | crc32(4 LE)`，crc32 覆盖前五段。

分片：`channel(1)=2 | op(1)=1 | total(2 LE) | cur(2 LE, 从 1 开始) | fragment`。

> 快应用的 prepare 字段号（`ThirdpartyApp{field22 → {1:package, 2:versionCode, 3:size}}`，命令 id=1）还没在真机上验证过，第一次测试建议先拿表盘练手。

字段号写错不会报错，只会让手表静默不理你 —— `tools/test_watchface_install.py` 就是把关键数字钉死的地方，改协议时先跑它。

## 安装卡在 mass_prepare 时怎么看串口

`mass_prepare` 的应答字段号最没把握，所以只要这一步没拿到合法状态，固件会无条件把原始回包打出来（不用改代码、不用开调试开关）：

```
WF_INSTALL_PREPARE_RAW mass len=14 08161000C2010A...
WF_INSTALL_PREPARE_SUB field=24 len=8 10 00 12 02 ...
WF_INSTALL_CAND sub=24 off=2=18
WF_INSTALL_CAND sub=24 off=5=2
```

- `_RAW` 是解密后的完整 protobuf
- `_SUB` 是外层 oneof（field 6 / 22 / 24）里的子字节串，逐层都能看到
- `_CAND` 是每个候选字节的十进制值 —— **位置无关**，故意不依赖 `Mass{2}/PrepareResponse` 这层包装，包装层猜错也能找到 `0`（成功）和 `expected_slice_length`

把这几行发给维护者，就能直接定位是哪一层字段号不对。
